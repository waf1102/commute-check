<task type="auto" tdd="true">
  <name>Task 2: Implement User Dependency and Update Endpoints</name>
  <files>
    - app/security.py
    - app/main.py
    - tests/test_api_auth.py
  </files>
  <behavior>
    - `get_current_user` should decode a JWT and return the corresponding User object.
    - `GET /config` should only return commutes for the authenticated user.
    - `POST /config` should associate the new commute with the authenticated user.
    - `DELETE /config/{id}` should only work if the commute belongs to the authenticated user.
  </behavior>
  <action>
    1.  In `app/security.py`, create a dependency function `get_current_user(token: str = Depends(oauth2_scheme)) -> User`. This function will decode the JWT, extract the user's email (or ID), and fetch the user object from the database. It should raise an `HTTPException` for invalid tokens.
    2.  Define `oauth2_scheme = OAuth2PasswordBearer(tokenUrl="api/login")` in `app/security.py`.
    3.  In `app/main.py`, inject this dependency into all endpoints that handle `Commute` data (`/config` GET, POST, DELETE).
    4.  Modify the logic in these endpoints:
        - `read_config`: The `select` statement must be filtered with `.where(Commute.user_id == user.id)`.
        - `create_or_update_config`: When creating a new commute, set `new_commute.user_id = user.id`. When updating, first verify the existing commute belongs to the user before saving changes.
        - `delete_config`: Verify the commute belongs to the user before deleting.
    5.  The `/assess` and `/test-webhook` endpoints can remain public for now as they are for manual, ad-hoc checks.
    6.  Create `tests/test_api_auth.py` to verify the new access-controlled behavior.
  </action>

    </automated>
  </verify>

## STRIDE Threat Register
| Threat ID | Category | Component | Disposition | Mitigation Plan |
|---|---|---|---|---|
| T-11-04 | Information Disclosure | Commute Data | Mitigate | All `Commute` data access in `/config` endpoints will be gated by a `Depends(get_current_user)` dependency. Queries will be strictly filtered by `user_id`, preventing User A from seeing User B's data. |
| T-11-05 | Tampering | Commute Data | Mitigate | `POST` and `DELETE` operations on `/config` will verify that the target `commute.user_id` matches the authenticated `user.id`, preventing unauthorized modification or deletion of other users' data. |
</threat_model>
